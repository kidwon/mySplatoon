# 技术决策与改进备忘录

> 记录每个已解决问题的方案、取舍理由，以及将来可以改进或替换的思路。
> 维护约定：每解决一个新问题就追加一节，格式统一为
> **问题 / 现方案 / 取舍理由 / 后续可尝试**。版本号对应 git tag。

## 1. 动态涂地（Turf System）`v0.1.0`

**问题**：子弹落地要在场地上留下持久的墨迹，且可随时查询任意位置的墨色。

**现方案**：地面贴图是一张 1024×1024 的离屏 Canvas 2D（`CanvasTexture`）。
落地时用 Canvas API 画"主墨斑（多个错位圆叠加）+ 随机小飞溅"，`needsUpdate`
刷新纹理。墨迹刻意使用**纯色填充**（不加渐变/噪声），保证像素采样判定稳定。

**取舍理由**：Canvas 2D 是最快落地的方案，绘制和查询天然同源（同一张画布），
不需要维护第二份数据结构；纯色是为判定服务的妥协。

**后续可尝试**：
- `WebGLRenderTarget` + 贴花着色器：墨迹可带法线/光泽/边缘发光，但查询需要
  `readRenderTargetPixels`（GPU 回读，有性能坑）或维护镜像数据。
- 墨迹带渐变/噪声纹理 + 判定改走覆盖网格（见 §3），解耦视觉与逻辑。
- 墙面/障碍物涂色：需要按面展 UV 或每面一张小 RenderTarget，工程量大，
  当前明确不做（子弹撞障碍物直接消弹）。

## 2. 墨色判定（潜行/回墨/减速）`v0.1.0`

**问题**：每帧判断角色脚下是己方墨、敌方墨还是干地。

**现方案**：对涂地 Canvas 做 1 像素 `getImageData` 采样（`willReadFrequently`），
与双方队伍色做每通道 ±46 的容差比对。

**取舍理由**：与视觉像素级一致（踩在飞溅小点上也算）；每帧一两次 1px 读取开销可忽略。

**后续可尝试**：
- 改用覆盖网格查询（O(1) 数组读取，无 Canvas 依赖），代价是精度降到格子尺寸
  （约 0.39m），墨迹边缘的判定会和视觉有出入。
- 若将来墨迹带渐变导致容差比对失效，这个切换就是必须的。

## 3. 覆盖率统计 `v0.1.0`

**问题**：实时显示双方涂地占比，结算时定胜负。

**现方案**：一张 128×128 的 `Uint8Array` 网格（0/1/2 = 未涂/紫/橙），
每次涂色时把主墨斑范围写入网格；统计时遍历 16384 格计数。

**取舍理由**：增量维护远比每秒扫描整张 1024 Canvas（4MB 像素回读）便宜；
16K 次循环每帧可跑。

**后续可尝试**：维护增量计数器（写格子时同步加减计数），把每帧遍历也省掉——
当前规模没必要，格子数量增大时再做。

## 4. 队伍颜色可选 `v0.1.0`–`v0.2.0`

**问题**：双方墨色可选，且不能破坏像素判定，也不能染花角色本体。

**现方案**：6 色调色板，**逐对校验过色距**（任意两色之间、与地板底色/网格线
之间至少一个 RGB 通道相差 ≥46，匹配判定容差）；撞色自动交换；换色触发整局
重置（旧墨迹无法重新上色）。角色换成ちいかわ后，队伍色不染身体，改为**发光
围巾**（`addTeamScarf`）+ 武器墨色部件。HUD 颜色统一走 CSS 变量
（`--player-color` / `--enemy-color`）。

**后续可尝试**：
- 自由取色器：需要运行时自动校验与另一方/地板的色距，不合格就拒绝或自动微调。
- 换色不重置：把判定全面切到覆盖网格（§2 的替代方案）后，旧墨迹只是颜色不变，
  归属仍正确，即可支持中途换色。

## 5. 命中与击倒 `v0.1.0`

**问题**：墨弹要能打中角色、造成伤害、击倒重生。

**现方案**：`HitTarget` 接口（玩家/机器人统一实现），子弹每帧做
"水平距离 + 高度区间"的胶囊近似碰撞。25 伤害/发；敌方墨汁 DoT（10/s，
下限 15 不致死）；己方墨潜行回血 35/s。击倒爆大墨迹 + 2.5s 重生。
反馈：受击闪白（emissive）、墨滴迸溅粒子、命中方准星脉冲。

**取舍理由**：两个目标 × 几十颗子弹的暴力遍历完全够用；胶囊近似对 Q 版
圆滚滚的角色误差很小。

**后续可尝试**：
- 摩擦/击退（被击中时位移）；无敌帧；重生保护。
- 命中部位差异（爆头？Q 版可能不需要）。
- 角色多时改空间哈希/网格加速碰撞查询。

## 6. 机器人 AI `v0.1.0`（难度）+ 障碍物版

**问题**：单人模式需要一个会抢地盘、有威胁但可调难度的对手。

**现方案**：两态行为机——**巡逻涂地**（随机选点、边走边喷、到点休息）与
**反击**（玩家在攻击距离内 + 未潜墨隐身 + 视线无遮挡时转火，带弹道下坠补偿
与按难度的散布）。三档难度参数表（移速/射速/墨迹大小/休息时长/反击距离/
瞄准散布），游戏中 1/2/3 即时切换。视线检测用 0.5m 步进采样 vs 障碍 AABB。

**后续可尝试**：
- 残血逃向己方墨汁回血（参数表已有 hp 概念，行为机加一个 flee 态即可）。
- 机器人也用乌贼形态潜行（隐身接近 + 快速转移）。
- 绕障碍寻路：当前撞到障碍靠推挤滑动 + 超时重选目标，A* 网格寻路会更聪明。
- うさぎ近战：近距离切换挥棒/泼桶砸人。
- 多机器人混战（2v2）：HitTarget 列表已支持多目标，主要是 AI 互相为敌的阵营逻辑。

## 7. 角色模型（img2threejs 流程）`v0.2.0`

**问题**：用ちいかわ角色替换胶囊体，无美术资源。

**现方案**：img2threejs（v1.5-beta）风格的**程序化建模**——纯代码工厂函数返回
`THREE.Group`，全部由命名部件（球/胶囊/锥/球面补丁）拼装。第一版凭公开设定
盲雕，第二版按参考图逐项修正（深色耳、高光眼、"ᆺ"嘴、八割花纹盖耳、
洗衣机泼桶等）。层级契约：`headGroup`（颈部枢轴）+ `handSocket`（道具挂点）
+ `userData.collider`。材质按实例克隆（`instantiateMaterials`），闪白/换色
不跨实例污染。

**取舍理由**：零资源文件、零加载时间、与 Vite 构建天然融合；Q 版色块角色
恰好是程序化基元的甜区。皮肤流程的自动评审门（Divine Eye 截图比对）在本
环境不可用（无浏览器截图通道），似度靠人工验收。

**后续可尝试**：
- 绒毛质感：噪声法线贴图（Canvas 生成）或 fresnel 边缘光 shader。
- ハチワレ花纹渐变：`onBeforeCompile` 注入顶点色渐变。
- 表情系统：脸部换成 CanvasTexture 贴片（参考图的 EXPRESSION_SPRITE 路线），
  可眨眼/受击表情/胜利表情。
- 乌贼形态专用模型：当前是整体压扁，可以做一个"趴地乌贼化"小模型切换。
- 接入浏览器截图通道后，用 img2threejs 的评审门跑一轮正式的似度评分。

## 8. 武器模型 `v0.3.0`

**问题**：角色空手，参考图给出了角色-武器配对与插槽结构。

**现方案**：四件程序化武器（墨枪/墨辊/洗衣机泼桶/蓄力狙），
`{ group, inkMats }` 结构把墨色部件材质单列供换色；`attachWeapon()` 挂到

**后续可尝试（优先级最高的玩法方向）**：
- **武器机制差异化**：辊类（贴地滚动涂色 + 近身碾压）、泼桶（扇形抛洒、
  高弧线）、蓄力狙（按住蓄力、一发直线贯穿涂色）。武器选择进开始界面。

- 开火时武器后坐/枪口墨光。

## 9. 移动"滑行感" `v0.4.0`

**问题**：角色移动时模型静止不动，像贴地滑行。

**现方案**：程序化摇摆步（`CharacterAnimator`）——按命名部件驱动：脚交替
前后摆+抬脚、手臂反摆、身体颠簸+左右 waddle、头部点头、耳朵甩动；步频随
移速；待机呼吸；跳跃收脚；乌贼游动快速摆尾。所有偏移基于构造时记录的
rest 姿态 × 平滑 blend 权重，停步自动归位无漂移。

**取舍理由**：Q 版短肢角色没有可弯的腿部关节，骨骼动画性价比低；
程序化正弦摆动 30 行代码就有 8 成效果。

**后续可尝试**：
- 骨骼版：img2threejs v1.5 的 rig 轨道（骨架 + geodesic voxel 蒙皮）+
  `THREE.AnimationMixer` 状态机（walk/run/jump/splat 动画剪辑）。
- 脚步 IK 贴地（斜坡/障碍上）；转身时身体倾斜；急停小趔趄。
- 脚步声与步频同步（AudioManager 已有节奏基础设施）。

## 10. 第三人称相机遮挡 `v0.4.0`

**问题**：相机吊臂穿进障碍物/围墙后面，角色被挡。

**现方案**：吊臂收缩（boom clamp）——每帧从头部沿相机方向做 slab 法
射线 vs AABB 测距（`cameraObstruction`，覆盖障碍物 + 四面围墙），被挡当帧
**瞬时收缩**到遮挡面前 0.25m（防穿模闪帧），解除后按 5 u/s **平滑弹回**；
最短 0.8m 不怼脸；保留 y≥0.4 地面保护。

**后续可尝试**：
- 低墙遮挡半透明（X-ray）：只对两道低墙做"挡视线时临时降透明度"，
  狭窄角落的频繁伸缩会舒服很多。注意障碍物材质当前是共享的，需按实例克隆。
- Whisker 预测射线：转角提前避让（塞尔达式），小场地收益有限。
- 相机碰撞体积（球扫掠而非单射线）：贴边时更稳。

## 11. 音效 `v0.1.0` 后期

**问题**：游戏全程静音，反馈感缺失；不想引入音频资源文件。

**现方案**：Web Audio API 全合成（`AudioManager` 单例）——振荡器包络
（射击/命中/受伤/击倒/重生/跳跃/嘀嗒/哨声）、噪声缓冲（溅落/踩镲）、
LFO 颤音（潜墨循环音）、16 步进 chiptune BGM（低音线/踩镲/旋律，前瞻调度）。
溅落声 70ms 节流防弹幕刷屏。M 键静音持久化。AudioContext 在首次点击手势启动。

**后续可尝试**：
- 换真实音源：只需改 `startBgm` 和各音效方法内部，接口不动。
- 空间音频（`PannerNode`）：机器人的脚步/射击声带方位，提升索敌信息量。
- 音量分轨设置界面（BGM/SFX 分开调）。

## 14. 自身遮挡准星/弹道（肩上视角）`v0.4.0` 后

**问题**：相机正对角色背后，角色（尤其ちいかわ体型的大脑袋）挡住屏幕中心的
准星目标；子弹从角色中心发射，起始弹道藏在身体里。

**现方案**：
- **肩上视角**：相机/瞄准共用的支点（`aimPivot`）在头部高度基础上向右肩
  偏移 0.75m，角色让到画面左下，准星视线畅通。相机遮挡收缩(§10)与准星射线
  都从这个支点出发，两套系统天然一致。
- **枪口出弹 + 准星收敛（muzzle-to-aimpoint）**：先沿相机中心射线求瞄准点
  （取地面交点 / 障碍 AABB 交点 / 40m 射程三者最近），再从武器枪口的世界
  坐标向瞄准点发射。顶墙时瞄准点若落在枪口之后，退回相机方向直射。

- **相机贴近淡出（已做，三个触发器）**：③相机→对手的视线被自己角色穿过时
  （垂距 < 1.0m 且角色位于相机与对手之间）淡出到 0.3，二值触发经 8/s lerp
  平滑——这是"对手被自己挡住"的直接解，对手位置由主循环每帧传入。另两个：①吊臂被遮挡压缩到 3.2m 以内时随
  距离淡出（下限 0.25）——注意默认俯视角会把相机抬到障碍物（≤2.2m）头顶之上，
  所以此触发器实际只在贴围墙/贴中央高台且视线接近水平时生效；②俯角低于
  -0.7 rad（低头涂脚下）时随俯角淡出（下限 0.35）——这才是"被自己大脑袋
  挡住"最高频的场景。两因素取 min，再与潜墨半透明相乘（`applyOpacity()`）。
  顺带修复：肩偏移可能把瞄准支点推进围墙内（射线起点在墙盒里导致吊臂
  永远压到最短），支点 x/z 现 clamp 在场内。已知小瑕疵：半透明时能隐约
  看到头内部的眼睛等内嵌部件（多 Mesh 透明排序通病），短暂出现可接受。
- **踩过的坑（重要）**：three.js 运行时把 `material.transparent` 从 false
  切到 true 需要 `needsUpdate` 重编译，否则 opacity uniform 更新了但混合
  不生效，材质看起来完全不透明（潜墨半透明因此从 v0.2 起一直是坏的）。
  正解：会淡出的材质在**创建时**就 `transparent: true`，运行时只改
  `opacity`（纯 uniform，即时生效，无重编译开销）。排查手段：HUD 临时
  调试读数（fadeDebug）区分"判定没触发"与"渲染没生效"。

**后续可尝试**：
- 左右肩切换（贴右墙时换左肩探头），一个按键把 SHOULDER_OFFSET 取反+平滑过渡。
- 瞄准点对敌人的软吸附（辅助瞄准）。
- 淡出改为棋盘格镂空 shader（dither），可避免透明排序瑕疵且不需排序开销。

## 15. 角色选择系统 `v0.6.0`

**问题**：玩家/对手角色写死在控制器里（ハチワレ/うさぎ），无法选择；
Player 与 Bot 的外观接线逻辑（材质克隆/围巾/武器/闪白/淡出）重复。

**现方案**：三层结构——
- **注册表** `models/characters.ts`：`CharacterDef` 收拢每角色的模型/武器
  工厂与差异参数（围巾挂点半径、碰撞胶囊、相机支点高度 camHeight）。
  新角色只加一行。顺带修正：旧围巾半径小于挂点高度处的头部截面半径，
  一直几乎埋在模型里——注册表按各体型几何重新标定。
- **外观代理** `CharacterAvatar.ts`：模型+动画器+围巾+武器的组装与状态
  （换色/闪白/透明度/乌贼压扁/枪口世界坐标/姿态重置）统一收口，
  Player/Bot 各持有一个，换角色 = 换实例（还掉了 §16 技术债一条）。
  武器新增 `muzzle` 标定（各武器局部坐标的出墨点），出弹不再硬编码
  墨枪偏移。
- **UI**：开始界面两行角色按钮（我的/对手，data-i18n 由 applyStatic
  统一填充，三语角色名），选中角色的展示台台座按队伍色发光，
  选择持久化 localStorage，换角色触发整局重置（大厅语义）。

- **角色选择页（已做）** `ui/CharacterSelect.ts`：独立 THREE.Scene 影棚
  （环境光+主光+冷色轮廓光、台座、队伍色发光环），复用主渲染器全屏渲染，
  主循环按 `charSelect.active` 切换渲染目标并跳过游戏世界更新。预览直接用
  CharacterAvatar（含围巾/武器/待机呼吸），自动旋转 + 拖拽旋转。
  UI：上方我的/对手页签、左右箭头循环、底部角色名 + 选定/返回，ESC 可退。
  开始界面入口按钮显示当前选择（动态文案，语言切换时手动刷新）。

**后续可尝试**：
- 选择页角色出场小动画（跳一下/挥武器）；按角色微调预览相机距离。
- 相机参数（吊臂长度）按角色体型微调（Q 版矮角色可拉近些）。
- 对手角色随机模式；双方同角色时用围巾色区分（已支持选同角色）。

### 15.1 乌贼形态替代模型（Doro 四脚姿势）

**问题**：乌贼形态一律"整体压扁"（scale 0.34），但 Doro 的标志姿势是
四脚着地的 meme 原形，压扁完全不像。

**现方案**：模型可选双形态约定——工厂在 root 下建两个子组并登记到
`userData.humanForm / squidForm`（squidForm 默认 `visible=false`）。
`CharacterAvatar.setSquid` 检测到这对字段就切换可见性，否则沿用压扁。
配套细节：
- 围巾挂到 `humanForm ?? root` 上，四脚形态时随人形组隐藏（不悬空）。
- `instantiateMaterials` 本就 traverse 整棵树，隐藏形态的材质同样被克隆
  并预置 transparent——潜墨半透/淡出对四脚形态直接生效。
- 四脚形态部件命名避开动画器契约名（`quad-leg-*` 而非 `foot-left`），
  防止 `getObjectByName` 抓错；发型/脸用共用 builder 按缩放系数生成两份。
- 碰撞不变：仍用 `CharacterDef` 的乌贼换算（r×0.85 / h×0.35），
  与四脚形态高度近似。

## 18. 联机对战（1v1，WebSocket 中继）`v0.7.0`

**问题**：单机手感已成型，需要两个浏览器之间实时对战；不想引入重型联网框架，
也不想把 three.js 里的弹道/碰撞逻辑再搬到服务端跑一份。

**现方案**：
- **中继服务器** `server/index.ts`（Node + ws，约 250 行，`npm run server`）：
  只管房间码（4 位、去易混字符）、席位/队伍分配（席位奇偶交替）、准备状态、
  开局倒计时与结束时钟、消息转发（附 `from`/`seq`）、ping/pong 时钟同步。
  协议类型放在 `src/net/protocol.ts`，服务器直接 import（tsx 运行），
  客户端与服务器共享一份定义。`MAX_PLAYERS` 常量 + `spawnFor()` 已按 N 人两队写好，
  开放 2v2 只需改上限。
- **权威划分（favor the shooter，无服务端模拟）**：
  - 自己的移动/墨槽/血量/倒地本机结算，20Hz 广播快照（`state`）；
  - 自己的子弹本机模拟：落地涂色 → `paint` 事件；命中远端玩家 → `hit` 事件，
    对方收到后自己扣血；被击倒方广播 `ko`（特效/音效）并在脚下涂大墨迹；
  - 远端玩家的子弹本机只做表现（`cosmetic` 子弹，不命中、不涂地），
    因为 fire 与 paint 经历相同单程延迟，表现子弹落地与 paint 到达基本同时；
  - 远端角色 `RemotePlayer` 只做快照插值（渲染滞后 100ms）+ 形态/动画/半透明。
- **本地队伍语义不变**：客户端仍用 `'player' | 'enemy'`，会话层做
  `TeamIndex ↔ Team` 映射；队伍色 = 该队席位最小玩家的选色，服务器开局时保证不撞色。
- **结算一致性**：覆盖率网格对同一组 paint 事件是确定性的（主斑半径由射手决定并随事件
  发送），但双方本地应用顺序可能不同；为避免"一边胜一边负"，结束时**房主上报覆盖率**，
  服务器广播作为唯一结果，非房主 2.5s 未收到则用本地兜底。
- **UI**：开始界面"联机对战"入口 → 大厅（服务器地址 / 建房 / 房间码加入 /
  玩家列表 / 选角（复用角色选择页）/ 选色（对方队伍已用色禁选）/ 准备）→
  全员准备 3 秒倒计时 → "点击进入战场"覆盖层锁鼠标 → 结算 → 返回房间可再战。
  ESC 释放鼠标时对局继续（世界照常更新，只是自己不动）。HUD 右上显示延迟。
- **验证**：`scratchpad/nettest.mjs` 风格的双客户端脚本跑通了建房/加入/满员拒绝/
  撞色处理/准备开局/五类转发/到时结束/房主结果/回大厅/重赛/中途断线全链路
  （服务器 `MATCH_MS` 环境变量可缩短一局用于测试）。浏览器端到端由用户验收。

**取舍理由**：中继 + 客户端权威是这个体量最省事的方案：零服务端游戏逻辑、
可本机 `npm run dev:all` 一键联调、部署到 Fly/Railway 免费档即可。代价是可作弊
（对方客户端说打中就打中），私用对战可接受。

**后续可尝试**：
- 2v2：`MAX_PLAYERS = 4`，大厅加换队按钮，结算/小地图已按列表处理。
- 断线重连：服务器保留席位 N 秒，客户端带 token 重进；当前断线 = 对局结束。
- 延迟补偿：远端子弹按 `fire` 到达延迟预推进（fast-forward），减少"看见弹道晚"。
- 服务端权威：把 `InkSystem` 的弹道/命中抽成无 three.js 依赖的纯函数模块，
  服务器跑一份做仲裁，即可防作弊，也是走向排位/匹配的前提。
- 部署：客户端 `VITE_WS_URL=wss://…` 指向线上中继；HTTPS 页面必须用 wss。

### 18.1 局域网全设备加入 `v0.7.1`

**问题**：v0.7.0 联机要分别暴露 Vite（`--host`）和中继两个端口，客户端默认地址
硬编码 `ws://<页面主机>:8787`，其他设备加入要人工传 IP，还容易和 localStorage 里
记住的旧地址打架。

**现方案**：单端口、同源、零配置。
- `server/lan.ts`：中继改挂在 `http.Server` 上，同端口托管 `dist/`（SPA 回退、
  `assets/` 带 hash 走 immutable 缓存、路径规范化限定在 dist 内），并提供
  `GET /info`（本机局域网 IPv4 列表）和 `/health`。绑定 `0.0.0.0`（`HOST` 可改）。
  启动时打印 localhost / 每个网卡 IP / `<hostname>.local` 三类地址，并用
  `qrcode-terminal` 打首个地址的二维码。`dist/` 缺失时只提供中继并给出提示。
- 客户端 `defaultServerUrl()` 改为同源 `ws(s)://<location.host>/ws`；
  `vite.config.ts` 设 `server.host = true` 并把 `/ws`、`/info` 代理到中继，
  因此开发（5173）/ 局域网（8787）/ 线上（同域部署）三种情况共用一套逻辑。
  大厅只在用户手改地址时才写 localStorage，默认地址不落盘。
- 大厅入口页调 `/info` 展示"其他设备打开"的地址列表（端口取自当前页面，
  开发与生产都正确）；拿不到就隐藏。
- 脚本：`npm run lan`（build + 启动）、`npm run check`（双 tsc）。

**取舍**：不做 UDP/mDNS 发现——浏览器无法收广播，`<hostname>.local` 由操作系统
自带的 Bonjour 解析即可，无需额外依赖；地址 + 二维码已够"扫码即入"。
手机能打开页面但操作依赖指针锁定与键盘，触屏控制是独立的后续项。

**验证**：Node 脚本确认 `/`、`/info`、`/health`、深路径回退与穿越路径都安全返回；
WebSocket 经 `/ws`、根路径、Vite 代理三条路都拿到 welcome；v0.7.0 的双客户端
全链路回归在 `/ws` 上全部通过。真机多设备由用户验收。

### 18.2 触屏操作（手机可玩） `v0.7.2`

**问题**：局域网入口做好后手机能打开页面、能进大厅联机，但点"点击进入战场"没反应——
全部操作都挂在 Pointer Lock 上（`startOverlay`/`enter-overlay` 点击直接
`canvas.requestPointerLock()`），iOS Safari 不支持这个 API、Android 支持也不稳定，
调用后既不报错也不触发 `pointerlockchange`，覆盖层永远不消失，`updateSolo`/
`updateOnline` 也一直卡在"未锁定"分支不跑玩家逻辑。

**现方案**：给 `Input` 加一条不依赖鼠标的第二输入通道，游戏逻辑本身不用改。
- `Input`：`touchKeys`（与键盘 `keys` 同名字空间，`isDown` 两边都查）、
  `setTouchKey(code, down)`、`addLookDelta(dx, dy)`（并入 `mouseDX/DY`，
  与真实 `movementX/Y` 同单位），以及 `touchActive` + `engaged` getter
  （`pointerLocked || touchActive`，取代所有 `input.pointerLocked` 判断）。
- `game/TouchControls.ts`（新）：纯手势翻译层，按 `Touch.identifier` 分别
  跟踪，移动摇杆和视角拖拽可以两指同时进行。落指时 X 坐标在左半屏 → 生成
  浮动摇杆（跟手指出现，不固定位置），归一化位移超过死区就置位合成的
  `KeyW/A/S/D`；右半屏拖拽 → 每帧位移累加进 `addLookDelta`。开火/跳跃按钮
  按住生效、松手即停，和键鼠语义一致；潜行做成**切换**按钮而不是按住——
  人形态才能开火（见 `updateShooting`），潜行时用不上开火键，但右手拇指
  同时"按住潜行"又要点开火不方便，切换更适合单手操作。右上角菜单按钮
  相当于桌面端的 ESC：调用同一个 `releaseControlsUI()`。
  `TouchControls.supported` 用 `matchMedia('(pointer: coarse)')` 判断是否
  展示，而不是 UA 嗅探或单纯 `ontouchstart in window`（后者在带触屏的笔记本
  上也会为真，容易误判）。
- `main.ts`：`start-overlay`/`enter-overlay` 的点击处理分支——支持触屏就
  直接 `touchActive = true` 显示虚拟按键并隐藏覆盖层，否则走原来的
  `requestPointerLock()`；`pointerlockchange` 里"未锁定"的分支、以及触屏
  菜单按钮，都收口到同一个 `releaseControlsUI()`；`endMatch`/`endOnlineMatch`
  原来直接调 `document.exitPointerLock()`，改成 `exitControls()` 顺带清空
  触屏状态，避免结算画面下面虚拟按键还亮着。
- 视口 meta 加 `maximum-scale=1, user-scalable=no`，避免拖拽视角时触发
  浏览器捏合缩放/双击缩放；触屏容器 `touch-action: none` + 每个手势事件
  `preventDefault()` 双重保险防止页面滚动。

**取舍**：摇杆离散映射到与键盘完全相同的四个方向键，没做真正的模拟量
（推多远都是同一个移动速度）——本作移动本来就是定速的（`BASE_SPEED` 常量），
模拟量在这个体量下收益很小，换来的是零改动复用 `PlayerController` 里所有
既有的移动/减速逻辑。视角拖拽增益先按 1:1 抄鼠标 `movementX` 的量级，
真机手感需要用户自己试后再调 `TouchControls.ts` 里的 `LOOK_GAIN`。

**验证**：`tsc`（client + server）与 `vite build` 通过。真机触屏手势（多指、
误触边界、iOS/Android 差异）无法在此环境验证，需要用户在手机上实测，
尤其是视角拖拽的灵敏度。
